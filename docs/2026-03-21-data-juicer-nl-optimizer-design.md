# Data-Juicer：自然语言生成 Pipeline 与优化子系统设计

**日期**：2026-03-21  
**状态**：草案 v2（经审查修订）  
**范围**：目标代码库为 **data-juicer**；本文档落在 **agentic_planner** 仓库，作为跨仓库需求/设计备忘。

---

## 1. 背景与目标

### 1.1 背景

- **data-juicer-agents** 中已实现「自然语言 → Data-Juicer 可执行配置/recipe」的能力；期望将 **该能力迁入 data-juicer**，agents 侧其余能力不在范围内。
- 优化能力 **借鉴** docetl 中「指令式改写 + 搜索式改进」的思路（含 MOAR/MCTS 类方法的灵感），但在 **Data-Juicer 原生配置** 上 **重新实现**。
- **不**引入 docetl 依赖，**不**与 docetl 的 pipeline YAML 方言或包产生运行时耦合；docetl 仅作方法与流程参考。

### 1.2 目标

1. 在 **data-juicer** 内提供 **Python API**（类/函数、配置对象、类型），用于：
   - **自然语言生成** DJ 原生可执行配置；
   - **可选的两阶段优化**：阶段一为配置文件驱动的 **指令式推理优化**；阶段二为 **搜索式优化**（v1 使用简化搜索策略，接口预留日后替换为 MCTS 等）。
2. 阶段一与阶段二之间、以及所有对外交付物均为 **DJ 执行器可直接加载运行的原生配置格式**（见第 2.3 节），保证「仅做阶段一」时产物可直接执行。
3. 用户可选择：**仅阶段一**、**仅阶段二**、**先一再二（串行）**。
4. **多目标**（成本 vs 质量）在概念上成立；**v1** 以 **多候选 + 每候选指标 + 人工选择** 为主，不强制完整 Pareto 前沿算法。

### 1.3 非目标

- 不在本设计范围内规定 **CLI / Web / 服务** 的具体封装（以 **API** 为主，应用层自行封装）。
- 不迁移 data-juicer-agents 中与会话 Shell、TUI、无关工具链绑定的功能。
- 不把 docetl 作为依赖或内部中间持久化格式。
- 不引入向量数据库或 embedding 模型等额外基础设施。

---

## 2. 架构总览

### 2.1 推荐模块划分

采用 **「共享契约 + 两个能力模块」**：

| 模块（建议名，实现时可调整） | 职责 |
|-----------------------------|------|
| **contracts**（或 `core`） | DJ 可执行配置的表示与校验、评测协议、价目表、LLM/judge 配置、错误类型等 **跨能力共享类型** |
| **plan / recipe_gen** | 自然语言 + 数据集上下文 → **DJ 可执行配置**（从 agents 迁入并贴合 DJ 仓库结构） |
| **optimize** | 指令引擎 + 可插拔搜索策略 + 执行与评测编排 |

依赖方向：`plan` → `contracts`；`optimize` → `contracts`；**optimize 不依赖 plan**（便于仅手写配置再优化）。

### 2.2 核心抽象（便于日后升级到 MCTS）

将以下四类职责 **解耦**，保证 v1 用简化搜索、后期替换为 **MCTS** 时主要更换「搜索器」实现：

1. **状态**：始终为 **可校验、可执行的 DJ 配置**（YAML 序列化形态与 DJ 执行器一致，见 2.3）。
2. **动作**：**指令（directive）** 对配置施加 **单步合法变换**；指令集合与语义 **完全在 DJ 侧定义**（见第 4.2 节）。
3. **评测**：在 **样本数据** 上执行 pipeline，得到 **成本指标** 与 **质量分**（见第 6 节）。
4. **搜索策略**：在「状态 + 动作 + 评测」之上做探索；v1 可为贪心/束搜索等；日后可换 **MCTS/UCB** 及更丰富的多目标处理。

### 2.3 「DJ 可执行配置」的精确定义

本设计中所有「DJ 原生格式」均指 **DJ 执行器可直接加载运行的配置 YAML**，即 `config_all.yaml` 风格：

```yaml
dataset_path: /path/to/data.jsonl
export_path: /path/to/output.jsonl
np: 4
text_keys: text
process:
  - text_length_filter:
      min_len: 10
      max_len: 50
  - language_id_score_filter:
      lang: en
```

其中 `process` 列表中每个元素为 `{算子名: {参数字典}}` 结构。

**与 agents 的 PlanModel 的关系**：data-juicer-agents 中的 `PlanModel`（使用 `[{name, params}]` 结构）属于 NL 生成过程中的 **内部中间表示**，在最终输出时须转换为上述 DJ 可执行格式。contracts 层应提供此 **PlanModel → DJ 可执行配置** 的序列化方法，确保往返一致性。

## 3. 用户可见模式

| 模式 | 行为 |
|------|------|
| **仅阶段一** | 读取指令优化配置 → 指令改写 → 输出可执行配置（及变换轨迹）；无搜索循环。 |
| **仅阶段二** | 以用户给定的 DJ 可执行配置为根 → 搜索 → 输出候选集与指标。 |
| **阶段一 + 阶段二（串行）** | 阶段一输出作为阶段二的 **根状态**；两阶段之间传递 **同一 DJ 可执行格式**。 |

## 4. 阶段一：指令式推理优化

### 4.1 驱动方式

- 以 **单一配置文件**（YAML/JSON）为主：声明启用的指令类型、最大步数、是否逐步确认等。
- **不**以自然语言作为阶段一的主输入（与「NL 生成配置」正交：NL 用于生成 **初始** 可执行配置，阶段一用 **显式配置** 驱动改写）。

### 4.2 指令（Directive）—— 在 DJ 算子模型上的落地

docetl 的 directive 围绕「带 prompt 的 LLM 操作」设计，DJ 的算子模型有根本差异。DJ 算子分为两大类，directive 需要分别设计：

**非 LLM 算子**（filter、deduplicator、selector、部分 mapper 等）——参数为阈值、语言代码、正则等，无 prompt。适用的 directive 类型包括：
- **调参数/阈值**（如 `min_len: 10` → `min_len: 20`）
- **算子排序优化**（轻量 filter 前置，重算子后移，减少下游数据量）
- **替换为等价算子**（功能等价但效率不同的算子互换）
- **删除冗余算子**（检测并移除无效或重复的处理步骤）

**LLM 算子**（API-based mapper/filter/aggregator 等，标记为 🔗API / 🌊vLLM）——含 model、prompt 等参数。适用的 directive 类型更接近 docetl 思路：
- **换模型**（更便宜或更强的 LLM）
- **改写 prompt**（澄清指令、拆分子任务）
- **加 gleaning**（多轮校验，提升单条处理质量）

**v1 范围**：两类各实现一个最小子集（例如各 2-3 种最常用的 directive），完整的 directive 集合在后续版本扩展。

### 4.3 审计轨迹

- 每个 directive 对配置产生 **一步** 变换；需记录 **可审计** 的轨迹（变换前后 diff、应用的 directive 名称与参数），便于调试与复现。
- v1 可采用 **静态注册** 的指令表；插件化注册表可作为后续增强，非 v1 必需。

## 5. 阶段二：搜索式优化

### 5.1 思路

- 借鉴 docetl MOAR 类方法中的 **扩展–评估–迭代** 思想，在 **DJ 可执行配置** 上实现，**不**依赖 docetl 代码。
- v1 使用 **简化搜索**（如贪心/束搜索）；接口层保留 **策略可插拔**，便于替换为 **MCTS**。
- 若 v1 简化搜索效果不足，可在 **不改变配置与指令契约** 的前提下升级为 MCTS/UCB，主要是替换搜索器实现。

### 5.2 输出形态（v1 与多目标）

- **目标维度**：**成本**（见 6.1）与 **质量**（见 6.2），均为多维度。
- **v1**：输出 **多个候选配置**，每个附带成本与质量指标，由用户 **人工选择** 最终采用哪一个；**不**要求实现完整 Pareto 前沿算法。

---

## 6. 评测：成本与质量

### 6.1 成本（Cost）—— 双维度

v1 同时度量两个成本维度：

| 维度 | 来源 | 说明 |
|------|------|------|
| **LLM token 成本** | 统计 pipeline 执行中所有 LLM 调用的 token 用量 | 不同模型的单价由用户在配置中提供（价目表或等价映射），用于将 token 转为可比的货币或归一化成本 |
| **执行时长** | 在样本子集上跑 pipeline 的 wall time | 反映非 LLM 算子（CPU/GPU 密集型操作）的计算代价；对纯 filter/dedup 型 pipeline 尤其重要 |

两个维度独立呈现，由用户自行权衡（v1 不做自动加权合成）。

### 6.2 质量（Quality）—— 基于样本的逐条评测

**评测流程**：
1. 从输入数据集 **采样** 若干条数据（样本量与随机种子可配置，确保可复现）。
2. 在样本上 **执行 pipeline**，得到处理后的输出。
3. 对 **每条输出** 由评测模块打分。
4. 取所有样本得分的 **平均值** 作为该候选配置的 quality。

**评测模式（混合）**：
- **有 ground truth**（配置中声明标注路径）：优先采用与标注对比的评测路径——可以是规则比较、也可以是 judge 辅助判定。用户有标注时评测更省事、更准确。
- **无标注**（常见场景）：以 **LLM-as-a-judge** 为主，judge 基于 **任务说明 + 原始输入 + 处理后输出** 做逐条打分或判定。

配置中须显式声明当前运行依赖 **哪种评测路径**，避免误用。

### 6.3 执行与样本

- 搜索过程中在 **样本子集** 上执行 pipeline，以控制成本与耗时。
- 样本范围、采样策略与随机种子在评测配置中指定，确保不同候选之间的可比性与可复现性。

## 7. 自然语言 → 可执行配置（自 agents 迁入）

### 7.1 迁入范围

仅迁入与「自然语言生成 DJ 可执行配置」直接相关的能力；会话式 CLI、TUI、其他工具链不在范围。

### 7.2 需要迁入/适配的子能力

| 子能力 | agents 中的对应 | v1 处理策略 |
|--------|-----------------|-------------|
| **算子选择** | `retrieve_operator_candidates`（向量/BM25 检索） | **不迁入向量检索**。采用两步策略：(1) 将 DJ 全量算子清单（名称 + 一句话描述 + 标签，约 194 个，~15-20K token）放入 LLM prompt，由 LLM 根据用户意图选出候选算子；(2) 仅对选中算子，通过 DJ 已有的 `OPSearcher` / `OPERATORS` 注册表拉取详细参数文档，再让 LLM 填具体参数。 |
| **数据集画像** | `inspect_dataset_schema` | 复用 DJ 已有的 analyze / dataset 能力，或做轻量适配 |
| **LLM 生成算子序列** | `ProcessOperatorGenerator` | 迁入核心逻辑；LLM 调用层对接 DJ 已有的 LLM 调用路径（如有），或在 contracts 层统一封装 |
| **Spec 组装与校验** | `build_dataset_spec` / `build_process_spec` / `build_system_spec` / `assemble_plan` / `plan_validate` | 迁入校验逻辑，但最终输出须转换为 DJ 可执行格式（见 2.3），而非 agents 的 PlanModel |

### 7.3 输出要求

最终输出必须为 **DJ 可执行配置格式**（见第 2.3 节），以便与执行器、优化器共用 contracts 层。内部可保留 PlanModel 作为中间态，但对用户不可见。

- **对外主界面**：**Python API**（稳定、可组合）。
- CLI、HTTP 服务、IDE 插件等由 **应用层** 封装，不属于本设计必须交付物。

## 9. 错误处理原则

- **配置校验失败**：尽早失败，错误信息包含 **字段路径** 或 **错误码**，便于程序化重试或修复。
- **单步执行或评测失败**：策略层可定义 **跳过、重试、剪枝**；v1 可采用「记录失败并继续探索其他分支」的保守策略，具体策略在实现阶段细化。
- **Judge / LLM 调用不稳定**：可配置重试、温度与 **解析失败回退**（实现阶段定义默认值）。

---

## 10. 测试策略（方向性）

- **单元测试**（无真实 LLM）：directive 变换、配置解析与格式转换、价目表与 cost 汇总（注入假 token 计数）。
- **契约测试**：注入 **假 executor** 与 **假 judge**，固定返回 cost/quality，验证搜索与候选列表行为。
- **集成测试**（可选、慢）：真实 LLM，标记为可选测试集。

## 11. v1 交付范围

集中列出 v1 的边界，避免散落各节时理解不一致：

| 维度 | v1 包含 | v1 不包含（后续扩展） |
|------|---------|----------------------|
| **NL → 配置** | 两步选算子（全量清单 + 按需详情）、LLM 生成、格式转换输出 | 向量检索、多轮对话式配置生成 |
| **阶段一指令** | 两类（LLM 算子 + 非 LLM 算子）各 2-3 种 directive；静态注册 | 完整 directive 集合、插件化注册 |
| **阶段二搜索** | 简化搜索（贪心/束搜索）；策略接口可插拔 | MCTS/UCB、完整 Pareto 前沿算法 |
| **成本** | LLM token 成本 + 执行时长，双维度独立呈现 | 自动加权合成、更细粒度资源计量 |
| **质量** | 样本逐条 LLM-as-a-judge + 可选 ground truth 对照；取平均 | 数据集整体统计特征评测 |
| **多目标输出** | 多候选配置 + 指标表，人工选择 | 自动推荐、非支配排序 |
| **对外界面** | Python API | CLI、Web 服务、IDE 插件 |
| **指令注册** | 静态注册表 | 动态插件加载 |

## 12. 演进路径

- **搜索算法**：v1 简化策略 → 若效果不足，在 **不改变配置与指令契约** 的前提下替换为 **MCTS** 等。
- **多目标**：v1 人工从候选中选 → 后续可加强 **非支配排序 / Pareto** 与自动推荐。
- **成本模型**：v1 双维度（token + 时长）→ 后续可增加更细粒度的资源计量（GPU 显存、IO 吞吐等）。
- **指令集**：v1 最小子集 → 后续扩充，可引入插件化注册。
- **NL → 配置**：v1 两步策略 → 后续可引入向量检索或更智能的算子推荐。

## 13. 开放问题（实现前需收敛）

1. **指令集 v1** 的具体最小集合：两类各选哪 2-3 种？需结合实际 DJ 算子使用频率与优化收益确定。
2. **Token 统计** 与 DJ 内各 LLM 算子的挂钩点（统一埋点位置）。
3. **Judge** 的 prompt 模板、输出格式（JSON 分数 / 分类）及解析失败策略。
4. **PlanModel → DJ 可执行配置** 的转换方法中，需要处理哪些边界情况（如 dataset 高级配置、system spec 字段的映射）。
5. **LLM 调用层**：迁入的 NL 生成能力使用的 LLM gateway 是复用 DJ 已有路径还是在 contracts 层统一封装。
